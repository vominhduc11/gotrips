Ngữ cảnh đầu vào cho Claude Code khi làm việc trong repo **GoTrips** — nền tảng đặt tour du lịch trực tuyến (MVP). Trả lời và viết comment bằng **tiếng Việt**, trừ khi người dùng yêu cầu khác.

## Tổng quan monorepo

| Thư mục | Vai trò | Công nghệ | Cổng (Docker) |
|---|---|---|---|
| `gotrips-api/` | Backend REST API | Spring Boot 4.1 (Maven), Java 25, JPA, Flyway, PostgreSQL, Spring Security, Actuator, springdoc-openapi | 8080 |
| `gotrips-admin/` | Trang quản trị (SPA) | React 19 + Vite 8 + TypeScript, phục vụ bằng nginx | 8081 → 80 |
| `gotrips-web/` | Website khách hàng | Next.js 16 (App Router) + React 19 + Tailwind CSS 4 + TypeScript | 3000 |
| (gốc) `docker-compose.yml` | PostgreSQL 17 + 3 service trên | | DB 127.0.0.1:5432 |

Tài liệu khác ở gốc repo: `README.md` (hướng dẫn chạy dự án cho người mới), `GoTrips_ERD_V9_Corrected.drawio` (sơ đồ cơ sở dữ liệu) và bốn sơ đồ draw.io: `GoTrips_Kien_truc.drawio` (tổng thể hệ thống, triển khai Docker, luồng đăng nhập, làm mới cache), `GoTrips_Chuc_nang.drawio` (use case và phân quyền, màn hình website, màn hình admin), `GoTrips_Luong_nghiep_vu.drawio` (đặt tour, đặt phòng, đặt vé, nhân viên xử lý đơn) và `GoTrips_Trang_thai.drawio` (vòng đời đơn và thanh toán, tour và khách sạn, chuyến khởi hành, loại phòng và lịch bay). Phạm vi MVP và phần đã làm, chưa làm ghi ở mục "Trạng thái hiện tại" ngay dưới.

### Trạng thái hiện tại
- `gotrips-api`: là **nguồn duy nhất** của dữ liệu và luật nghiệp vụ cho website. Có **xác thực** (`V1__create_users_and_roles.sql`; `V11__add_user_phone.sql` thêm số điện thoại tuỳ chọn; `POST /auth/register`, `POST /auth/login`, `GET /auth/me`, `PUT /auth/me`, `PUT /auth/me/password`; JWT HS256 bằng OAuth2 Resource Server), **dữ liệu công khai cho website** (`V2__create_catalog_and_newsletter.sql`: điểm đến, tour + lịch khởi hành, khách sạn + loại phòng, sân bay + chặng bay, đánh giá, đăng ký ưu đãi; `V3__create_flights.sql`: hãng bay + lịch bay; `V4__add_room_inventory.sql`: tổng số phòng mỗi loại; `V9__hotel_images_and_amenities.sql`: danh mục tiện ích `amenities` với bảng nối `hotel_amenities`, `hotel_room_type_amenities` thay cột `hotels.amenities`, và bộ ảnh `hotel_images`, `hotel_room_type_images`), **tìm vé** (`GET /flights`, `GET /flights/{scheduleId}`), **đơn đặt chỗ** (`V5__create_bookings.sql`; `POST /bookings/tours|hotels|flights`, `GET /bookings/me`, `GET /bookings/{code}`), **đăng nhập quản trị** qua cookie phiên, **quản lý đơn** cho STAFF/ADMIN (`GET /admin/bookings`, `GET /admin/bookings/{code}`, ba thao tác trên đơn), **quản trị điểm đến, tour, lịch khởi hành** (`/admin/destinations`, `/admin/tours`, `/admin/departures`; `V7__catalog_soft_delete_and_departure_rules.sql`), **quản trị khách sạn, loại phòng** (`/admin/hotels`, `/admin/room-types`, `GET /admin/amenities`), **quản trị hãng bay, sân bay, lịch bay và chặng phổ biến** (`/admin/airlines`, `/admin/airports`, `/admin/flight-schedules`, `/admin/flight-routes`), **số liệu Tổng quan** (`GET /admin/dashboard`), **hồ sơ khách hàng**, **quản trị nhân viên**, **đổi mật khẩu quản trị** và **thanh toán chuyển khoản tự động qua webhook SePay** (`V10__create_bank_transactions.sql`; `POST /payments/sepay/webhook`, `GET /bookings/{code}/payment-status`, `/admin/bank-transactions`). Xem mục "gotrips-api". **Chưa có:** thanh toán thẻ/ví điện tử, hoàn tiền tự động, hạn giữ chỗ cho đơn chưa trả tiền, API quản trị danh mục tiện ích, cách ngừng bán lịch bay còn đơn trong tương lai, giới hạn số lần đăng nhập sai.
- `gotrips-admin`: đã có đăng nhập/đăng xuất qua API thật, kiểm phiên STAFF/ADMIN, khung điều hướng, trang Tổng quan với KPI, biểu đồ, việc cần làm và chuyến sắp khởi hành, danh sách và chi tiết đơn đặt chỗ cho nhân viên, quản lý điểm đến, tour và lịch khởi hành, quản lý khách sạn và loại phòng, quản lý hãng bay, sân bay, lịch bay và chặng phổ biến, tra cứu khách hàng và hồ sơ đơn, quản lý nhân viên cho ADMIN, đổi mật khẩu từ menu tài khoản, đối chiếu giao dịch ngân hàng do SePay báo (xem mục "gotrips-admin" bên dưới).
- `gotrips-web`: Đã có trang **Tài khoản của tôi** (`/account`) cho khách đăng nhập, sửa họ tên và số điện thoại, xem email và đổi mật khẩu. Trang chủ, tour (`/tours`), **khách sạn** (`/hotels`, `/hotels/[slug]`, `/hotels/[slug]/book`), **vé máy bay** (`/flights`, `/flights/book`) và **đơn đặt chỗ** (`/bookings`) đã dựng xong. **Mọi dữ liệu nghiệp vụ (danh mục, chuyến bay, đơn, thông tin chuyển khoản) lấy từ gotrips-api; web không còn dữ liệu giả** (xem "Trang chủ lấy dữ liệu từ API" bên dưới). Cả ba dịch vụ đều tìm → xem → đặt được (xem mục "Khách sạn" và "Vé máy bay" bên dưới). `/tours` lọc/sắp xếp/phân trang bằng URL search params (`destination`, `q`, `date`, `guests`, `sort`, `page`; parse bằng `lib/schemas/tour-filters.ts`, **API tính** kết quả qua `GET /tours`, ánh xạ tham số ở `lib/data/tour-request.ts`, cache ở `lib/data/tours.ts`), partial prerender: tiêu đề tĩnh, danh sách stream trong `<Suspense>`. Trang chi tiết `/tours/[slug]` đã có (`generateMetadata`, JSON-LD `TouristTrip`; gồm giới thiệu, lịch khởi hành, đánh giá, thẻ giá; **không có `generateStaticParams`**, xem bullet "Tour" bên dưới). `page.tsx` **không `await params`**: chỉ truyền Promise xuống `TourDetail` bọc trong `<Suspense fallback={<TourDetailSkeleton />}>`, vì App Shell dùng chung cho mọi liên kết tới route nên không được buộc vào một slug (nếu không dev overlay báo "URL data outside of Suspense"; `/hotels/[slug]` và `/hotels/[slug]/book` làm giống hệt qua `HotelDetail` và `BookHotelContent`). Trang `/tours/[slug]/book` làm giống hệt: `page.tsx` chỉ truyền Promise xuống `BookTourContent` (`components/booking/BookTourContent.tsx`) trong `<Suspense>`. **Luồng đặt tour** (đơn thật qua gotrips-api):
- **Chọn chuyến ở trang chi tiết** (không còn bước "Chọn lịch"): thẻ `TourBookingCard` (dính bên phải) có ô chọn ngày (`Select` shadcn) + số khách + tiền tạm tính + nút "Đặt tour"; chuyến gần nhất còn chỗ được chọn sẵn. Nút "Chọn ngày này" (`SelectDepartureButton`) ở `DepartureList` chỉ **chọn chuyến trong thẻ** rồi focus ô ngày (chuyến đang chọn hiện "Đã chọn"), không mở trang đặt tour. Tour hết chỗ thì nút "Đặt tour" bị khoá.
  - Form chọn chuyến nằm ở `TourBookingProvider` (client, bọc cả cột nội dung lẫn thẻ; nội dung vẫn là Server Component qua `children`). Ô ngày + số khách là `TripSelectionFields`, tiền tạm tính là `TripPriceBreakdown` (dùng chung với trang đặt tour). Luật đổi chuyến/hạ số khách: `changeTripDeparture`, chọn mặc định: `resolveTripSelection` (`lib/booking/steps.ts`, có test).
  - Lựa chọn đồng bộ với URL trang chi tiết (`?departure&guests`) **không dùng `useSearchParams`** (để giữ static shell): đọc `window.location` trong `useLayoutEffect` sau mount, ghi bằng `replaceState` qua `form.subscribe` (không dùng `watch(callback)` vì React Compiler bỏ qua). Nhờ vậy Back từ trang đặt tour và liên kết `buildTourBookingHref` (`/tours/[slug]?departure&guests#dat-tour`) điền sẵn được.
  - "Đặt tour" gọi Server Action `startBookingAction`: server kiểm phiên rồi `redirect()` tới `/book?departure&guests` hoặc `/login?next=…`. **Không** điều hướng client tới `/book` để `BookingGate` chuyển sang đăng nhập: Next (`cacheComponents`) giữ cây `/book` vừa ghé trong `<Activity>` kèm lệnh chuyển hướng, đăng nhập xong quay lại `/book` thì bị đẩy về `/login` lần nữa (có e2e).
- **Trang đặt tour 2 bước, lưu trên URL:** `?departure&guests&step=thong-tin|xac-nhan`, parse/build bằng `lib/schemas/booking.ts` (`step=chon-lich` cũ rơi về `thong-tin`). `BookingWizard` (client) dùng **một** form RHF cho cả 2 bước.
  - `BookingGate` (server): URL thiếu chuyến / chuyến hết chỗ → `redirect` về thẻ "Đặt tour" ở trang chi tiết (giữ số khách); chưa đăng nhập → `/login?next=<URL đang mở>`.
  - Đổi ngày / số khách ngay tại trang bằng hộp thoại `ChangeTripDialog` (nút "Thay đổi" ở `BookingSummaryCard`, "Sửa lịch" ở bước Xác nhận): form nháp riêng, "Áp dụng" mới ghi vào đơn, thông tin đã nhập được giữ. Hộp thoại phải nằm **ngoài** `<form>` của wizard (sự kiện React nổi bọt qua portal). Lỗi server về chuyến/số khách hiện thành lỗi chung ở đầu form.
  - Chuyển bước bằng `window.history.pushState`, không dùng `router.push`, vì `router.push` làm page segment mount lại và mất state form.
  - Thông tin cá nhân không đưa lên URL. Vì vậy URL đòi "Xác nhận" khi thông tin chưa hợp lệ thì `resolveBookingStep` (`lib/booking/steps.ts`, có test) đưa về "Thông tin" rồi `replaceState`.
  - Nhấn Enter ở bước "Thông tin" chỉ là "Tiếp tục", chưa tạo đơn.
  - **URL là nguồn sự thật của chuyến + số khách**, đã chuẩn hoá bằng `normalizeBookingSelection` (`lib/booking/steps.ts`). Khi điều hướng client-side tới cùng route với search params khác (ví dụ quay lại trang chi tiết rồi bấm "Đặt tour" với ngày khác), Next **dùng lại** `BookingWizard` đang có, nên `useForm` không đọc lại `defaultValues`.
    - Vì thế wizard có effect đồng bộ form theo URL, khai báo trước effect sửa URL.
    - Form nào khởi tạo từ URL cũng phải đồng bộ theo URL như vậy, không chỉ đọc URL lúc mount (có e2e).
- **Đăng nhập:** `next` được lọc bằng `getSafeRedirectPath` (`lib/safe-redirect.ts`, chống open redirect); đăng nhập xong quay lại đúng URL trang đặt tour.
  - `LoginForm`/`RegisterForm` đọc `next` trong `onSubmit` chứ không lúc render, để `/login` vẫn tĩnh.
  - Liên kết qua lại giữa `/login` và `/register` là `AuthSwitchLink` (`components/auth/`, href dựng bằng `buildAuthHref`) nên giữ `next`: gắn vào `href` sau mount, và đọc URL lại lúc bấm vì chỉ đổi query trên trang đang mở (vd bấm "Đăng nhập" ở Header) không chạy lại effect (có e2e). Liên kết đăng nhập/đăng ký ở Header và menu điện thoại không mang `next`.
- **Tạo đơn (chung cho tour, khách sạn, vé):** `createBookingAction` (`lib/actions/booking.ts`), `createHotelBookingAction`, `createFlightBookingAction` chỉ kiểm lại schema (báo lỗi sớm) rồi gọi `POST /bookings/...` bằng token của phiên; **không gửi giá**. API tự tính tiền, giữ chỗ trong transaction và trả mã `GT` + 6 ký tự; đơn mới là `PENDING` với thanh toán `UNPAID`. Phần gọi API và xử lý lỗi dùng chung ở `lib/actions/booking-submit.ts` (không `"use server"`):
  - Thiếu token hoặc API trả 401 → `redirect` tới `/login?next=<trang đang đặt>`.
  - 400/409 kèm `errors[]` → `fromApiFieldErrors` (đổi `travelers[0].fullName` thành `travelers.0.fullName`) gắn vào ô; field mà form không có thì hiện `detail` ở đầu form. Thêm field mới thì khai ở regex `*_FORM_FIELD` của action (và danh sách lỗi chung đầu form của wizard).
  - Mạng/5xx → "Hệ thống đang bận…"; log không ghi dữ liệu người dùng hay token.
  - Thành công → làm mới cache bằng `after(() => revalidateTag(tag, { expire: 0 }))` (tour: `tours`, `departures`; phòng: `hotels`; vé: `flights`). **Không** gọi thẳng `updateTag`/`revalidateTag` trong action: phản hồi sẽ render lại trang đặt chỗ đang mở, và khi vừa hết chỗ thì gate của trang tự chuyển hướng, tranh với việc form đưa khách sang trang đơn. E2E canh cả hai phía (đặt hết ghế vẫn tới trang đơn; trang tour hiện số chỗ mới, tắt revalidate thì test đỏ).
- **Trang `/bookings` và `/bookings/[code]`** ("Đơn đặt chỗ của tôi", chung cho tour/khách sạn/vé): Server Component đọc `lib/data/bookings.ts` (server-only: Bearer từ `getSessionToken`, `no-store`, KHÔNG `"use cache"`) qua `loadSection` trong `<Suspense>`. Chưa đăng nhập hoặc 401 → `/login?next=`; API lỗi → `SectionUnavailable` (**không** dựa vào `getCurrentUser` để quyết định: API sập thì nó coi như khách và sẽ đẩy sang đăng nhập). Mã sai định dạng (`isBookingCode` ở `lib/booking/booking-code-format.ts`, kiểm TRƯỚC khi gọi API vì client Orval không mã hoá đường dẫn), mã không có hoặc đơn của người khác → 404. DTO được đổi sang view chung ở `lib/data/booking-view.ts` (`highlights`, `priceLines`, `people`, `flightSegments`; có test), nên `BookingHistory`/`BookingDetail` không rẽ nhánh theo loại.
  - Trang chi tiết có hướng dẫn chuyển khoản lấy từ `bankTransfer` của API: nội dung = mã đơn, `amountDue` (tổng tiền trừ phần đã nhận) và ảnh VietQR `qrImageUrl` (API dựng; null khi chưa đặt `GOTRIPS_BANK_QR_CODE`; hiện bằng `next/image` `unoptimized`). SePay báo tiền vào API, đủ tiền thì đơn tự xác nhận (xem "Thanh toán SePay" ở mục gotrips-api); nhân viên vẫn đánh dấu đã thu, xác nhận và huỷ ở `/bookings` của gotrips-admin.
  - Khi đơn đang chờ tiền, `PaymentStatusWatcher` (client) hỏi lại mỗi 5 giây qua Route Handler `app/api/bookings/[code]/payment-status` (proxy đọc cookie phiên, `no-store`, 401/404/503), thấy trạng thái hoặc số đã nhận đổi thì `router.refresh()` để Server Component dựng lại. Luật ở `lib/booking/payment-status.ts` (có test): chỉ hỏi khi tab đang mở, ngừng sau 180 lần hoặc khi 401/404. Số lần đã hỏi chỉ có trên state của query (`getQueryState`), kết quả `useQuery` không có `dataUpdateCount`. E2E `payment.spec.ts` gửi webhook có chữ ký thật; cần `GOTRIPS_SEPAY_WEBHOOK_SECRET` trùng với API đang chạy, thiếu thì bỏ qua.
- **Đơn đọc bằng Server Component** (token chỉ server đọc được). TanStack Query chỉ dùng để hỏi lại trạng thái thanh toán ở trang chi tiết đơn, qua Route Handler proxy (xem trên).
- **Khách sạn** (cùng khuôn với tour): **tìm và chi tiết đọc gotrips-api** (`lib/data/hotels.ts`: `searchHotels` → `GET /hotels`, `getHotelDetail` → `GET /hotels/{slug}`, `getHotels` → `GET /hotels/featured?limit=50`; xem bullet "Khách sạn" ở mục "Trang chủ lấy dữ liệu từ API"). JSON-LD `Hotel` có `image` là mảng và `amenityFeature`.
  - `/hotels`: phần đọc URL (`HotelSearchSection`) nằm trong `<Suspense>`. Đổi lại các trang tour không còn được prerender sẵn từng slug lúc build (vẫn cache theo `cacheLife` của `getTourDetail`).
    - Lỗi API: `TourListing` thay danh sách bằng `SectionUnavailable` (thanh lọc vẫn hiện); `TourDetail`/`BookTourContent` hiện `SectionUnavailable`; `generateMetadata` rơi về tiêu đề chung. Mọi lời gọi đi qua `loadSection` nên `next build` không chạm API (đã kiểm: build với `API_URL` trỏ vào cổng chết vẫn qua).
  - **Khách sạn** (`/hotels`, `/hotels/[slug]`, `/hotels/[slug]/book`; `lib/data/hotels.ts`): `searchHotels(query)` → `GET /hotels?destination&checkIn&checkOut&guests&rooms`, `getHotelDetail(slug)` → `GET /hotels/{slug}`, `getHotels()` (gợi ý của `/hotels`) và `getFeaturedHotels(limit)` (Trang chủ) → `GET /hotels/featured` (gợi ý dùng `limit=50`, tối đa của API; không có endpoint riêng). **API chọn phòng rẻ nhất đủ chỗ, tính tổng tiền cả kỳ và sắp theo tổng tiền** (`HotelStayCalculator`; web không còn `searchHotels`/`findHotelDetail` ở `hotel-view.ts`, chỉ còn hàm nhỏ cho tạm tính trên giao diện). Điểm cần nhớ:
    - Các luật cần "hôm nay" hoặc so sánh nhiều tham số (ngày nhận ≥ hôm nay, trả > nhận, ≤ 30 đêm, `rooms ≤ guests`) kiểm ở service và ném `InvalidRequestException` → 400 `errors[{field,message}]` (cùng câu chữ với `checkStayDates` ở web); web đã kiểm trước nên 400 hiếm gặp, nếu gặp thì `loadSection` coi như lỗi API (`SectionUnavailable`).
    - `HotelDetailView` là alias của DTO, `roomTypes` của nó kiểu `HotelRoomTypeDetailView` (thêm `images`, `amenities`); `HotelSearchResultView.room` giữ `HotelRoomTypeView` (không `hotelId`); `checkInTime`/`checkOutTime` là chuỗi "HH:mm" do API định dạng.
    - **Slug qua `isValidHotelSlug`** (`lib/data/hotel-request.ts`) trước khi gọi API, cùng lý do với tour (kể cả chặn `featured`). Schema `destination` của form tối đa 100 ký tự (khớp API, và để khoá cache của `searchHotels` không phình).
    - **Không có `generateStaticParams`** ở `/hotels/[slug]` và `/hotels/[slug]/book`; `page.tsx` không `await params`, chỉ truyền Promise xuống `HotelDetail`/`BookHotelContent` trong `<Suspense>` (cùng khuôn tour). Slug không có, khách sạn không ACTIVE hoặc hết loại đang bán → API 404 → `getHotelDetail` trả `null` → `notFound()`. URL cũ mang `?room=` của loại đã ngừng bán được trang chi tiết đổi sang loại còn bán. Trang đặt phòng chuyển về trang chi tiết để chọn lại.
    - Lỗi API: `HotelSearchSection` thay riêng khối kết quả/gợi ý bằng `SectionUnavailable` (form vẫn dùng được); `HotelDetail`/`BookHotelContent` hiện `SectionUnavailable`; `generateMetadata` rơi về tiêu đề chung. Đã kiểm với `API_URL` trỏ cổng chết: build qua và các trang khách sạn hiện "Chưa tải được…".
  - **Cache** nằm trong bộ nhớ tiến trình. Hai nguồn làm hết hạn ngay: web tự gọi `revalidateTag` sau khi **chính nó** tạo đơn, và API gửi webhook (`POST /api/revalidate`, khi đã bật) sau khi nhân viên huỷ đơn hoặc ghi danh mục qua `/admin`. Dữ liệu đổi theo đường khác (sửa DB, đơn tạo từ client khác) chỉ đổi sau khi hết `cacheLife` (`minutes`/`hours`/`days`). API loại đánh giá của tour HIDDEN hoặc DELETED; `getTestimonials` vì vậy gắn cả tag `tours` (webhook không nhận tag `testimonials`).
  - **Newsletter**: form ở `NewsletterCta` gọi Server Action `subscribeNewsletterAction` (`lib/actions/newsletter.ts`) → `POST /newsletter/subscriptions`. Thành công/lỗi đều báo bằng toast Sonner; thành công còn hiện lời cảm ơn tại chỗ; lỗi theo ô gắn lại qua `fromApiFieldErrors`; lỗi mạng/5xx → "Hệ thống đang bận…" (`lib/actions/messages.ts`, dùng chung với đăng nhập); log không ghi email. API trả 204 cả khi email đã đăng ký nên form không biết email mới hay cũ. Luật email có ở cả `lib/schemas/newsletter.ts` lẫn `SubscribeNewsletterRequest` của API: đổi một nơi phải đổi nơi kia.

### Lưu ý môi trường (máy dev Windows của người dùng)

- Test E2E của dự án dùng `@playwright/test` trong `gotrips-web` (nếu đã cài). Chỉ khi cần kiểm tra giao diện nhanh, ngoài bộ test, mới dùng `playwright-core` đặt trong thư mục scratchpad, và không cài thêm vào repo.
- **`JAVA_HOME` mặc định là JDK 17** (dự án cần 25) và máy không có JDK 24/25. Chạy test API trong container JDK 25 (Testcontainers dùng Docker của máy qua socket); từ gốc repo, trong Git Bash:
  ```bash
  MSYS_NO_PATHCONV=1 docker run --rm -v "$(cygpath -wa gotrips-api):/app" -v gotrips-m2:/root/.m2 \
    -v /var/run/docker.sock:/var/run/docker.sock -e TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal \
    -w /app eclipse-temurin:25-jdk ./mvnw -B test
  ```

  Không kéo được image từ Docker Hub thì thêm tiền tố `mirror.gcr.io/library/`.
- Git Bash đổi đường dẫn bắt đầu bằng `/` thành đường dẫn Windows (`curl http://localhost:3100/` thành `C:/Program Files/Git/`): đặt `MSYS_NO_PATHCONV=1` khi gọi `curl` tới đường dẫn gốc.

## Quy ước chung
- **Không commit** `.env`, `.env.*` (trừ `.env.example`) hay bí mật. Mật khẩu DB chỉ nằm trong `.env`.
- **Biến môi trường kết nối API** (mẫu ở `.env.example` của từng dự án và ở gốc repo; `docker-compose.yml` đã truyền `API_URL` cho web, `GOTRIPS_JWT_SECRET` cấu hình cookie/hạn JWT admin và 3 biến `GOTRIPS_BANK_*` cho api):

  | Dự án | Biến | Ý nghĩa |
  |---|---|---|
  | web | `API_URL` | Địa chỉ API mà web gọi từ phía server. Mặc định `http://localhost:8080`; trong Docker là `http://gotrips-api:8080` |
  | admin | `VITE_API_URL` | Mặc định `/api` cùng origin. Vite và nginx bỏ tiền tố này khi chuyển đến API |
  | admin | `VITE_WEB_URL` | Website khách cho liên kết "Xem trên website", nhúng lúc build. Mặc định `http://localhost:3000`; Docker build nhận qua build arg cùng tên, `docker-compose.yml` lấy từ file env của Compose (không đặt thì dùng mặc định) |
  | api | `GOTRIPS_CORS_ORIGINS` | Các origin được gọi API từ trình duyệt (admin), cách nhau bằng dấu phẩy. Mặc định `http://localhost:8081,http://localhost:5173` |
  | api | `SPRINGDOC_ENABLED` | `false` để tắt `/v3/api-docs` (mặc định `true`) |
  | api | `GOTRIPS_JWT_SECRET` | **Bắt buộc**, khoá ký JWT (HS256), tối thiểu 32 byte; không có mặc định có chủ đích (khoá lộ = giả mạo được token, kể cả ADMIN) nên thiếu thì API không khởi động. Đặt trong `.env` ở gốc repo (compose bắt buộc), tạo bằng `openssl rand -base64 48`. Mỗi môi trường một khoá riêng |
  | api | `GOTRIPS_JWT_EXPIRATION` | Thời hạn access token, dạng Duration của Spring (`7d`, `12h`...). Mặc định `7d`, khớp hạn cookie phiên của web |
  | api | `GOTRIPS_JWT_ADMIN_EXPIRATION` | Hạn JWT admin, mặc định `8h`, cũng là hạn cookie phiên |
  | api | `GOTRIPS_ADMIN_COOKIE_SECURE` | Mặc định API là `true`. Compose local dùng `false` cho HTTP. Đặt `true` khi phục vụ qua HTTPS |
  | api | `SPRING_PROFILES_ACTIVE` | `seed` nạp dữ liệu mẫu (`db/seed`: danh mục, lịch bay, tài khoản quản trị) và tài khoản nhận chuyển khoản thử nghiệm. `docker-compose.yml` mặc định `seed` cho dev/Docker; **môi trường thật phải đặt rỗng** (`SPRING_PROFILES_ACTIVE=` trong `.env`). Không đặt = không nạp (chạy mvnw) |
  | api | `GOTRIPS_WEB_REVALIDATE_URL` | URL web nhận yêu cầu làm mới cache. Để trống thì tắt (mặc định của Compose). Muốn bật trong Compose thì đặt `http://gotrips-web:3000/api/revalidate` trong `.env` (mẫu đang là dòng comment ở `.env.example`) |
  | api, web | `GOTRIPS_REVALIDATE_SECRET` | Bí mật riêng dùng chung giữa API và web, chỉ đọc lúc chạy; tạo bằng `openssl rand -hex 32` |
  | api | `GOTRIPS_CATALOG_ALLOWED_IMAGE_PREFIXES` | Tiền tố URL ảnh mà trang quản trị được lưu, cách nhau bằng dấu phẩy. Mặc định `https://images.unsplash.com/photo-`. Đổi ở đây thì phải đổi `images.remotePatterns` (`gotrips-web/next.config.ts`) và `img-src` (`gotrips-admin/nginx.conf`). Compose khai biến **không kèm giá trị**, giống 3 biến ngân hàng |
  | api | `GOTRIPS_BANK_NAME`, `GOTRIPS_BANK_ACCOUNT_NUMBER`, `GOTRIPS_BANK_ACCOUNT_NAME` | Tài khoản nhận chuyển khoản hiện ở trang chi tiết đơn. **Bắt buộc có giá trị** (thiếu thì API không khởi động) trừ khi bật profile `seed`, profile này có sẵn giá trị thử nghiệm. `docker-compose.yml` khai 3 biến **không kèm giá trị** để chỉ truyền khi `.env` có đặt (viết `${VAR:-}` sẽ truyền chuỗi rỗng, đè mất giá trị thử nghiệm) |
  | api | `GOTRIPS_SEPAY_WEBHOOK_SECRET` | Secret Key HMAC-SHA256 của webhook SePay (`POST /payments/sepay/webhook`), phải trùng khoá đặt ở SePay; tạo bằng `openssl rand -hex 32`. Tuỳ chọn: để trống thì API tắt nhận webhook (endpoint trả 404), nhân viên đánh dấu đã thu bằng tay. Compose khai **không kèm giá trị** như 3 biến ngân hàng |
  | api | `GOTRIPS_BANK_QR_CODE` | Mã ngân hàng cho ảnh VietQR ở trang đơn (`VCB`, `MB`, mã BIN `970436`...). Tuỳ chọn: để trống thì trang đơn không có mã QR. Compose khai không kèm giá trị |

## Quy tắc dùng thư viện (BẮT BUỘC, áp dụng cho cả 3 dự án)

Mục tiêu: session nào cũng dùng đúng thư viện đã chốt, **không "code chay"** lại thứ thư viện đã làm được, và cũng **không dùng thư viện sai chỗ**.

1. **Đọc manifest trước khi viết code.** Mở `package.json` (web, admin) hoặc `pom.xml` (api) của dự án đang sửa và đối chiếu với các bảng bên dưới.
2. **Thư viện đã cài thì bắt buộc dùng.** Không tự viết lại chức năng mà thư viện đã cài cung cấp: quản lý form, validation, fetch/cache phía client, component UI, icon, toast, xử lý ngày, bảng dữ liệu, map DTO, test.
3. **Thư viện có trong bảng nhưng chưa cài:** không viết tạm bằng code tay, cũng không tự chọn thư viện khác thay thế. Dừng lại, báo người dùng và đề xuất lệnh cài đúng thư viện trong bảng.
4. **Thư viện ngoài bảng:** không tự thêm. Phải hỏi người dùng trước. Khi được duyệt thì cập nhật bảng trong file này cùng lúc với việc cài.
5. **Đúng phạm vi.** "Dùng triệt để" nghĩa là dùng thư viện cho đúng việc ghi ở cột "Dùng cho". Không đưa thư viện vào những chỗ ghi ở cột "Không dùng cho".

## gotrips-api (Spring Boot)

- Package gốc: `com.gotrips.gotrips_api` (lưu ý dấu gạch dưới). Cấu hình ở `src/main/resources/application.yaml`.
- **Schema do Flyway quản lý**, Hibernate chỉ `ddl-auto: validate` → mọi thay đổi bảng phải là file migration mới trong `src/main/resources/db/migration` (`V1__...`, `V2__...sql`), không sửa migration đã áp dụng. Chỉ dùng kiểu cột `integer/bigint/numeric/varchar/boolean/date/time/timestamptz/text/uuid` (`uuid` cho id người dùng và các cột tham chiếu tới nó): Hibernate so kiểu cột nghiêm ngặt khi `validate` (`smallint` không khớp `Integer`, `numeric(2,1)` cần `BigDecimal`). **Dữ liệu mẫu** nằm ngoài migration: `src/main/resources/db/seed/R__seed_catalog.sql` (migration lặp lại của Flyway), chỉ được nạp khi bật profile `seed` (`application-seed.yaml` thêm `classpath:db/seed` vào `spring.flyway.locations`); idempotent (`ON CONFLICT DO NOTHING` + `setval` cho sequence IDENTITY, vì id được chèn tường minh; riêng hai bảng ảnh để id tự sinh, `UNIQUE (chủ, sort_order)` chặn nhân đôi, và `SeedDataTests` chạy lại cả file để canh). Flyway chạy lại file đã đổi nên dòng MỚI tự vào DB cũ, còn dòng đã có (ví dụ mô tả khách sạn) giữ nguyên: muốn nạp lại phần đã sửa thì `docker compose down -v`. Cũng vì `ON CONFLICT DO NOTHING`, nếu nội dung file đổi thì tiện ích, ảnh hay loại phòng mà admin đã gỡ khỏi khách sạn mẫu có thể bị chèn lại (chỉ ảnh hưởng DB dev). Seed là bộ dữ liệu mẫu DUY NHẤT cho dev/Docker và E2E (web không có bản sao); vài giá trị cố định được `SeedDataTests` canh. Seed có trong jar nhưng không chạy nếu không bật profile.
- `open-in-view: false` → không lazy-load ngoài transaction; map sang DTO trong service.
- Bảo mật ngoài `/admin/**` (`config/SecurityConfig.java`): stateless, CSRF tắt, xác thực bằng **JWT Bearer** (OAuth2 Resource Server; không còn HTTP Basic). Công khai: `/actuator/health/**`, `/v3/api-docs/**`, `/swagger-ui/**` (để Orval đọc spec), `POST /auth/register`, `POST /auth/login`, và dữ liệu cho website: `GET /destinations`, `/airports`, `/tours` (tìm), `/tours/*` (chi tiết `/tours/{slug}`, gồm cả `/tours/featured`; `*` chỉ khớp MỘT đoạn nên `/tours/{slug}/gì-đó` vẫn cần token), `/hotels` (tìm), `/hotels/*` (chi tiết `/hotels/{slug}`, gồm cả `/hotels/featured`; `/hotels/{slug}/gì-đó` vẫn cần token), `/flights` (tìm vé), `/flights/*` (một lịch bay), `/flight-routes/popular`, `/testimonials`, `POST /newsletter/subscriptions`, `POST /payments/sepay/webhook` (không có token, kiểm bằng chữ ký HMAC ở controller); còn lại, gồm `GET /auth/me`, `PUT /auth/me`, `PUT /auth/me/password` và `/bookings/**`, cần token. Khi thêm endpoint công khai cho website phải mở rõ ràng **từng đường dẫn** trong cấu hình này (không dùng `/tours/**`, `/hotels/**`: các endpoint chi tiết/đặt chỗ sau này không được vô tình thành công khai; có test `PublicEndpointsTests` canh điều này). Đã có bean CORS (`gotrips.cors.allowed-origins`) cho admin; web gọi từ server nên không cần CORS.
- **Xác thực quản trị** (`AdminSecurityConfig`, `AdminAuthController`), chain stateless riêng cho `/admin/**`. `GET /admin/auth/me` cấp cookie CSRF `XSRF-TOKEN` cả khi trả 401. `POST /admin/auth/login` và `POST /admin/auth/logout` cần header `X-XSRF-TOKEN`. Login trả `UserResponse` và cookie `gotrips_admin_session` (`HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` theo env), đồng thời thay cookie CSRF. Logout trả 204 và xoá cả hai cookie. Các thao tác ghi còn lại chỉ cần CSRF khi dùng cookie. Bearer được ưu tiên và vẫn dùng được cho API đơn. Vai trò admin đọc từ DB mỗi request: thiếu/không hợp lệ/đã xoá tài khoản → 401, mất STAFF/ADMIN → 403. `/admin/staff/**` chỉ cho ADMIN. Chưa có giới hạn lần đăng nhập sai hoặc thu hồi JWT trước hạn.
- **Tài khoản chỉ dành cho dev** (`R__seed_admin_accounts.sql`, profile `seed`): `admin@gotrips.test` / `GoTripsDevAdmin26` (ADMIN) và `staff@gotrips.test` / `GoTripsDevStaff26` (STAFF). Seed chỉ gán vai trò cho bản ghi vừa tạo. API ghi WARN chung khi profile này bật. `SeedDataTests` đăng nhập thử cả hai tài khoản.
- **Xác thực** (package `auth/`, `user/`): bảng `users` (UUID, email luôn chữ thường — có `CHECK`, `password_hash`, `full_name`, `phone varchar(30)` từ V11), `roles` (CUSTOMER/STAFF/ADMIN, seed ở V1), `user_roles`. Đăng ký công khai luôn là CUSTOMER (request không có trường vai trò). Mật khẩu băm bằng `DelegatingPasswordEncoder` (bcrypt, lưu dạng `{bcrypt}...`). `AuthService.login` luôn chạy một lần so khớp mật khẩu kể cả khi email không tồn tại (không lộ email nào đã đăng ký qua thời gian phản hồi) và trả cùng một thông báo cho sai email/sai mật khẩu. Email trùng → 409 kèm `errors[{field:"email"}]` (kiểm trước + ràng buộc UNIQUE của DB là chốt chặn khi hai request đồng thời).
- **Hồ sơ và mật khẩu** (`auth/AuthService`): `PUT /auth/me` cập nhật họ tên và số điện thoại của chủ token. Bỏ trường `phone`, gửi `null` hoặc chuỗi trống thì xoá số. API dùng `common/validation/PhoneRules` chung với `ContactRequest` và DB chặn số rỗng bằng `users_phone_not_blank`. `UserResponse.phone` là trường bắt buộc có mặt, nhận chuỗi hoặc `null`, kể cả trong phản hồi đăng nhập/xem phiên của admin. `PUT /auth/me/password` trả 204, kiểm mật khẩu hiện tại và giới hạn 72 byte UTF-8, dùng chung logic băm với đổi mật khẩu quản trị. Hai thao tác khoá hàng `users` và Hibernate cập nhật `updated_at` khi có thay đổi. JWT đã cấp vẫn hợp lệ tới khi hết hạn.
- **JWT** (`config/JwtConfig`, `config/JjwtDecoder`, `JwtProperties`, `auth/JwtService`): HS256 bằng jjwt, claim `sub` = id người dùng, `roles` = ["CUSTOMER"] (→ authority `ROLE_CUSTOMER`), `iss` = `gotrips-api`. `JjwtDecoder` implement `JwtDecoder` của Spring (trả về `Jwt` của Spring nên controller vẫn dùng `@AuthenticationPrincipal Jwt`); **chỉ nhận HS256** (bỏ dòng `.sig().clear()...` thì token HS384 được chấp nhận, có test canh), bắt buộc có `exp`, kiểm issuer + hạn (lệch đồng hồ 60 giây). Token hỏng phải ném `BadJwtException` (loại khác thành 500) với thông báo **ASCII** (Spring đưa vào header `WWW-Authenticate`). Cả ký lẫn kiểm dùng giờ hệ thống, không dùng bean `Clock`. Token chỉ chứa thứ cần để phân quyền; email, họ tên và số điện thoại lấy từ `GET /auth/me`. Chưa có refresh token/thu hồi. Mật khẩu tối đa **72 byte** (annotation `@MaxUtf8Bytes` ở `common/validation`): BCrypt ném `IllegalArgumentException` (→ 500) nếu vượt, mà `@Size` chỉ đếm ký tự nên không đủ cho chữ có dấu.
- **Danh mục công khai cho website** (package `destination/`, `tour/`, `hotel/`, `flight/`, `testimonial/`, `newsletter/`; Controller → Service → Repository; service đọc `@Transactional(readOnly = true)`; không N+1: `join fetch`/một query gom theo danh sách id). Điểm đến, tour, chuyến khởi hành, khách sạn, loại phòng, hãng bay, sân bay, lịch bay và chặng bay ghi được qua API quản trị. Đánh giá và danh mục tiện ích **chỉ để đọc**. `tour_departures.booked_seats` chỉ đổi bằng câu UPDATE khi đặt/huỷ. Entity chỉ map cột cần dùng (tour đã map `short_description`; khách sạn đã map mô tả và giờ nhận/trả phòng (`LocalTime`); loại phòng map đủ tên/sức chứa/giường/diện tích; tiện ích và ảnh là entity riêng: `Amenity`, `HotelImage`, `HotelRoomTypeImage` và hai entity bảng nối `HotelAmenity`/`HotelRoomTypeAmenity` dùng `@IdClass`, không `@ManyToMany`. `ddl-auto: validate` **không kiểm khoá chính**, khai khoá sai chỉ lộ qua test). API là **nguồn duy nhất** của các luật dưới đây (web không có bản tính riêng):
  - Tour/khách sạn `HIDDEN` hoặc `DELETED` (xoá mềm) không được trả hay đếm ở bất kỳ API công khai nào (cả đánh giá của tour đó): truy vấn công khai luôn lọc `status = ACTIVE`. Đơn đã đặt vẫn đọc được.
  - Chuyến **đóng bán** (`sales_closed`) được tính như còn 0 chỗ ở mọi đường công khai và ở lệnh giữ chỗ (`TourCardCalculator`, `findBookable`, truy vấn tour nổi bật, `reserveSeats`): website hiện "Hết chỗ", hình dạng API công khai không đổi. Dưới đây, "chuyến đặt được" = sau hôm nay, đang mở bán và còn chỗ.
  - `/tours/featured` (mặc định `limit` 8): tour ACTIVE + `is_featured` còn ít nhất một chuyến đặt được (`departure_date > hôm nay` và còn chỗ), theo id, `limit` áp dụng SAU khi bỏ tour hết chuyến. Các trường suy ra tính ở `tour/TourCardCalculator` (hàm thuần, có test): giá từ = chuyến đặt được rẻ nhất (hoà giá → chuyến sớm hơn) kèm giá gốc/% giảm của CHÍNH chuyến đó; ngày gần nhất + số chỗ còn lại = chuyến đặt được sớm nhất; `isAlmostFull` = còn ≤ 5 chỗ.
  - `GET /tours` (tìm tour; `TourService.search` + `TourSearchCalculator`, hàm thuần có test): query `destination` (slug), `q`, `date` (`YYYY-MM-DD`), `guests` (1–50), `sort` (`FEATURED` mặc định, `NEAREST_DEPARTURE`, `PRICE_ASC`, `PRICE_DESC`, `RATING`), `page` (≥ 1); **8 tour/trang cố định** (`PAGE_SIZE`). Trả `{ items: TourCardResponse[], total, page, pageCount, destinationName }`. Luật: chỉ tour ACTIVE; slug điểm đến không tồn tại → kết quả rỗng (không bỏ qua bộ lọc), `destinationName` null; `q` so khớp không phân biệt dấu/hoa thường (kể cả `đ → d`) trên "tên tour + tên điểm đến"; `date`/`guests` chọn các CHUYẾN còn đặt được thoả điều kiện và thẻ hiển thị giá/ngày của đúng các chuyến đó, tour không có chuyến nào thoả thì bị loại; không lọc ngày/khách thì tour hết chỗ vẫn hiện (không có giá) và **mọi kiểu sắp xếp đều xếp tour không có giá xuống cuối**, hoà thì theo id (trang 1/2 không trùng hay sót); `page` vượt quá được kẹp về trang cuối (kẹp TRƯỚC khi nhân để không tràn int), `pageCount` tối thiểu 1. **Lọc/sắp/phân trang làm trong bộ nhớ** (đủ cho catalog cỡ MVP: một query tour + một query chuyến đặt được cho cả danh sách); khi catalog lớn phải đẩy xuống SQL.

> **Quan trọng:** đây là Next.js 16 với breaking changes so với kiến thức cũ. `gotrips-web/AGENTS.md` yêu cầu đọc tài liệu trong `gotrips-web/node_modules/next/dist/docs/` **trước khi viết code Next.js**. Chú ý các deprecation notice.

### Cấu hình đáng chú ý (`next.config.ts`)
- `output: "standalone"` (Docker chạy `node server.js`), `cacheComponents: true`, `partialPrefetching: true`.
- Tailwind 4 chạy qua `@tailwindcss/turbopack` (khai báo trong `turbopack.rules`).
- Ảnh remote chỉ cho phép `images.unsplash.com/photo-*`.

- `POST /api/revalidate` nhận tag danh mục từ API, so header `X-Gotrips-Revalidate-Secret` bằng `timingSafeEqual`, kiểm danh sách cho phép rồi gọi `revalidateTag(tag, { expire: 0 })`. Lượt đọc website kế tiếp lấy dữ liệu mới sau khi webhook tới. Route này cần bí mật kể cả khi API chưa bật webhook.

### Cài / thêm shadcn trên Windows (các lỗi đã gặp)
- Windows không phân biệt hoa/thường: tên file trong `components/ui/` phải chữ thường (`button.tsx`). Nếu từng có `Button.tsx`, git index (`core.ignorecase=true`) sẽ giữ tên cũ — kiểm tra `git ls-files components/ui` trước khi commit.
- `shadcn add` sinh `import { cn } from "cn"` (npm package `cn`, không dùng). Sau mỗi lần add phải sửa thành `@/lib/cn`, và không cài package `cn`.
- `shadcn add` các component phụ thuộc `button` sẽ hỏi ghi đè `button.tsx`/`badge.tsx` (đã tuỳ biến theo GoTrips). Sao lưu trước, hoặc trả lời "không"; nếu dùng `-o` thì khôi phục lại hai file này.
- `button.tsx` chỉ có size `sm|md|lg|icon|icon-sm|icon-lg` và variant `primary|accent|outline|ghost`. Component shadcn dùng `size="default"` hay variant khác (`secondary`, `destructive`, `link`) sẽ lỗi tsc: đổi sang giá trị có sẵn hoặc thêm vào `button.tsx` cho đúng token.
- `next-themes` không dùng (chỉ chế độ sáng): `sonner.tsx` cố định `theme="light"`.
- Vitest 5 (rolldown) trên Windows có thể báo "Cannot find native binding": chạy `npm install @rolldown/binding-win32-x64-msvc --no-save` (lỗi optional-deps của npm, không ghi vào package.json).
Alias import: `@/*` → thư mục gốc `gotrips-web/`.

### Quy tắc kiến trúc dữ liệu
- Component chỉ lấy dữ liệu qua `lib/data/*` (không gọi thẳng client Orval hay `fetch`); ghi dữ liệu qua Server Action. **Web không có dữ liệu giả**: màn hình mới cần dữ liệu API chưa có thì làm API trước. Test đơn vị viết dữ liệu ngay trong file test, gõ kiểu bằng DTO của Orval; E2E lấy giá trị kỳ vọng từ API.
- **Hàm data đọc dữ liệu công khai** (danh mục, tour, khách sạn, chuyến bay) vừa phải `"use cache"` vừa **không được chạy lúc `next build`** (build không có API): gọi chúng qua `loadSection` (có `await io()`) từ component bọc `<Suspense>`, xem "Trang chủ lấy dữ liệu từ API". `await params`/`searchParams` hoặc `connection()` ở trang cũng đưa phần đó ra khỏi build (`/tours`, `/hotels`, `/flights`), nhưng **không nên chỉ dựa vào đó** (`partialPrefetching` có thể prerender tiếp): vẫn gọi qua `loadSection`.
- Vì `cacheComponents` bật và logic "ngày còn chỗ" phụ thuộc thời điểm hiện tại, các hàm data phải nằm trong phạm vi `"use cache"` để trang prerender được thành static shell. Dùng `getTodayInVietnam()` (`lib/data/tour-view.ts`), không dùng `new Date()` rải rác. **Client Component cũng không được đọc "hôm nay" lúc render** (client component vẫn prerender trên server, build sẽ lỗi): chỉ tính trong panel lịch (chỉ render khi mở Popover) hoặc trong hàm validate/submit, như `DatePickers.tsx` và `createHotelSearchSchema()`. E2E Trang chủ phải đợi hydrate xong (`gotoHome` trong `e2e/home.spec.ts`), nếu không bấm "Tìm" sớm sẽ submit form kiểu HTML thuần.
- Dữ liệu "View" (tourCount, giá thấp nhất, ngày khởi hành gần nhất...) do **API tính sẵn**, không lưu trong DB. Tour và khách sạn trạng thái `HIDDEN` hoặc `DELETED` không được hiển thị/đếm; khách sạn hết loại phòng đang bán cũng rời website.
- Admin ghi điểm đến/tour/lịch khởi hành → API gửi webhook với tag `tours`, `departures`, `destinations`; ghi khách sạn/loại phòng → tag `hotels`, `destinations` (cả 404 đã cache khi hết loại đang bán cũng được làm mới). Ghi hãng/lịch bay → `flights`, ghi sân bay → `airports`, ghi chặng phổ biến → `flight-routes`. `getTestimonials` gắn `testimonials` và `tours` (các tag đang dùng: `site`, `destinations`, `tours`, `departures`, `hotels`, `flight-routes`, `flights`, `airports`; `getFeaturedHotels` gắn thêm `destinations` vì thẻ hiện tên điểm đến, `getPopularFlightRoutes` gắn `airports` vì thẻ hiện tên sân bay/thành phố).

### Giao diện / design tokens
- Nguồn duy nhất của màu, bo góc, đổ bóng, font là khối `@theme` trong `app/globals.css`. Bảng màu mặc định của Tailwind **đã bị xoá** (`--color-*: initial`) → chỉ dùng token: `primary-*` (teal), `accent-*` (cam, cho giá/CTA), `neutral-*`, `danger/success`, alias `surface`, `ink`, `ink-muted`, `line`; `rounded-control|card|pill`; `shadow-card|card-hover|search|header`. **Không hard-code mã màu.**
- Chỉ có chế độ sáng. Chữ trắng chỉ đặt trên `primary-700+` / `accent-700+` để đạt tương phản AA.
- Font: Be Vietnam Pro (subset `vietnamese` + `latin`, khai báo weight).
- `cn()` (`lib/cn.ts`) = `clsx` + `tailwind-merge` (`extendTailwindMerge`): gộp class xung đột, class sau thắng. Đã khai báo token riêng `rounded-control|card|pill`, `shadow-card|card-hover|search|header`, `max-w-page`. **Thêm token mới vào `@theme` thì phải khai báo thêm ở `lib/cn.ts`**, nếu không không gộp được (có test ở `lib/cn.test.ts`).
- **Khi dùng shadcn:** biến `--accent` của shadcn là **nền khi hover** (được gán sang `primary-50`). Nó khác với dải màu cam `accent-*` của GoTrips dùng cho giá và CTA. Cần màu cam thì dùng `accent-700`; không dùng `bg-accent` với ý là màu cam.
- Accessibility: giữ skip-link "Bỏ qua điều hướng", `id="noi-dung-chinh"`, focus ring theo token `focus`.
- **Ảnh hiện tại là ảnh Unsplash tạm** (placeholder, không phải ảnh thật của địa danh) — phải thay bằng ảnh thật/có bản quyền trước khi ra mắt (URL nằm trong seed `R__seed_catalog.sql` của API và `lib/site-content.ts`).

## Docker
- Cả 3 Dockerfile là multi-stage trên `node:24-alpine` (web, admin) và build Maven (api). Web chạy non-root.
- Thứ tự khởi động: `gotrips-db` (healthy) → `gotrips-api` (healthy) → `gotrips-admin` & `gotrips-web`. Thứ tự này chỉ áp dụng cho lúc CHẠY: `docker compose up --build` build mọi image trước khi khởi động container nên API chưa chạy lúc build web — vì vậy web không được gọi API lúc `next build` (xem "Trang chủ lấy dữ liệu từ API"; Dockerfile web không cần `ARG API_URL`).
- `gotrips-api` chạy với `SPRING_PROFILES_ACTIVE=seed` mặc định trong compose (dữ liệu mẫu, tài khoản quản trị và tài khoản chuyển khoản thử nghiệm). Môi trường thật đặt profile rỗng, `GOTRIPS_ADMIN_COOKIE_SECURE=true` và 3 biến `GOTRIPS_BANK_*` (dùng SePay thì thêm `GOTRIPS_SEPAY_WEBHOOK_SECRET`, `GOTRIPS_BANK_QR_CODE`; URL webhook đặt ở SePay là `<địa chỉ API>/payments/sepay/webhook`, cổng 8080 của API đang mở trong Compose).
- **`.env` chỉ dùng cho máy local; triển khai VPS dùng `.env.vps`** ở gốc repo (không commit, khớp `.env.*` trong `.gitignore`). File này đặt sẵn cấu hình môi trường thật (profile rỗng, webhook bật, bí mật riêng, `VITE_WEB_URL` theo địa chỉ VPS), còn phải điền 3 biến `GOTRIPS_BANK_*`. VPS hiện chạy bằng IP qua HTTP nên tạm đặt `GOTRIPS_ADMIN_COOKIE_SECURE=false` (trình duyệt bỏ cookie `Secure` trên HTTP, admin không đăng nhập được); có tên miền + HTTPS thì đổi lại `true`. Chạy `docker compose --env-file .env.vps up -d --build`; có `--env-file` thì Compose không đọc `.env`, nên mọi lệnh compose trên VPS đều phải kèm cờ này. Profile rỗng thì DB chưa có tài khoản quản trị: đăng ký ở website rồi gán vai trò ADMIN bằng `INSERT INTO user_roles` (lệnh mẫu ở `.env.vps`).
- Cổng DB chỉ bind `127.0.0.1:5432` để chạy API bằng IDE/mvnw, không lộ ra mạng ngoài. Nghiệm thu stack riêng bằng Compose project khác, tệp env riêng và override cổng. Soát tên project, cổng, network và volume với `docker compose config` trước khi chạy.
